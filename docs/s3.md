# Integrated S3 access

STQR serves S3 directly from its existing HTTP server at `/s3/`, on every node
running this implementation. There is no gateway process or extra port. The
namespace library in `client/s3.go` uses ordinary bucket objects and CAS; the
server adapter adds HTTP, AWS Signature V4 and the existing user/bucket grants.
This endpoint inherits the native object's current placement capabilities; adding
HTTP handlers does not add remote object routing or replication by itself.

Create a dedicated bucket (for example `fop-files`) and user in the dashboard,
grant that user access, then open **Users → S3-Schlüssel** to generate credentials.
Copy the secret before closing the dialog. Keys are stored inside the user record
in the system bucket. Revoking a key, disabling/deleting its user, or removing a
bucket grant affects subsequent S3 requests. READ permits GET/HEAD/LIST, WRITE
permits PUT, copy destinations, multipart initiation/parts/completion/abort;
DELETE permits DELETE and DeleteObjects. Copy sources need READ separately. Write-only and delete-only grants work;
internal metadata access does not expose a native read capability to those users.

Use the same settings as FOP's AWS PHP client:

```php
$s3 = new Aws\S3\S3Client([
    'version' => 'latest',
    'region' => 'eu-west-1',
    'endpoint' => 'http://localhost:7419/s3',
    'use_path_style_endpoint' => true,
    'credentials' => ['key' => $accessKey, 'secret' => $secretKey],
]);
$s3->putObject([
    'Bucket' => 'fop-files', 'Key' => '123:',
    'Body' => fopen('upload.bin', 'rb'), 'ACL' => 'private',
]);
$result = $s3->getObject([
    'Bucket' => 'fop-files', 'Key' => '123:', 'Range' => 'bytes=0-1023',
]);
```

For FOP, set `S3Url` to the endpoint including `/s3`, `S3Bucket` to the bucket
name, and `S3Key`/`S3Secret` to the generated credentials. This adapter was tested
with aws/aws-sdk-php 3.407.1 using FOP's path-style/`eu-west-1` configuration.

## Supported operations

- PUT with strings/streams, private ACL, standard content headers and `x-amz-meta-*`.
  Bodies are staged locally to compute checksums before publishing the complete
  native object. Temporary files are unlinked immediately and closed on every
  completion/failure; process termination also releases their storage. Staging
  needs local disk space.
- GET, HEAD and single byte ranges (closed, open-ended or suffix), ETag and
  Last-Modified, conditional GET and `If-Range`. Private objects remain private.
- Conditional PUT with `If-Match` or `If-None-Match: *`.
- Idempotent DELETE, using native version-checked object deletion to free the
  metadata and payload in one atomic storage transaction.
- ListObjects v1/v2 with prefix, delimiter, marker/continuation token, start-after,
  `max-keys` and URL encoding. Bucket HEAD checks access. Pagination is a sequence
  of current views, not a frozen multi-request snapshot.
- SigV4 header authentication and presigned URLs. A signing region is accepted as
  part of the signature scope; it does not choose STQR placement. Signed payload
  SHA-256, Content-MD5 and supplied CRC32/CRC32C/CRC64NVME/SHA1/SHA256 checksum headers are
  verified before publishing an object.

- Multipart: CreateMultipartUpload, UploadPart, ListParts, ListMultipartUploads,
  CompleteMultipartUpload and AbortMultipartUpload, including pagination. Parts
  are numbered 1–10000 and at most 5 GiB; all except the final selected part must
  contain at least 5 MiB. Completion preserves multipart ETags (`digest-count`).
  CRC32/CRC32C support composite or full-object checksums; SHA1/SHA256 composite;
  CRC64NVME full-object checksums.
- CopyObject with COPY/REPLACE metadata directives and source preconditions,
  plus UploadPartCopy with optional source ranges. Both remain inside the server.
- DeleteObjects: up to 1000 keys, quiet mode, independent errors per key and
  request checksum validation.
- ListBuckets (accessible buckets only), GetBucketLocation and GetBucketVersioning.
  Versioning reports an unversioned bucket; the protocol region is `eu-west-1`,
  independent of placement. The existing catalog does not store creation dates;
  ListBuckets uses the Unix epoch as its explicit unknown-date sentinel.
- AWS streaming modes `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`,
  `STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER` and
  `STREAMING-UNSIGNED-PAYLOAD-TRAILER`. Signed chunks and trailer signatures,
  declared decoded lengths and checksum trailers are checked before publication.
  As with AWS unsigned-payload requests, use TLS or localhost for unsigned data.

Buckets are created through STQR administration. Public ACLs, versioning,
nonempty tagging, general lifecycle policies, SSE and SigV4A remain unsupported.
For untagged objects, GetObjectTagging truthfully returns an empty set; setting
or deleting an empty set works. Nonempty tags are rejected rather than discarded.
This permits ordinary copy tools' tag-discovery requests.

## Multipart storage, recovery and cleanup

A multipart upload is one native object in format **STMU v1**, with binary
metadata and a compact concatenation of its current parts. Replacing a part
atomically replaces that object and releases the previous allocation. No
unindexed detached part objects are created. Upload IDs and part data survive
node restart and can be resumed with the same credentials/user.

Complete first persists its selected parts and target publication preconditions.
Recovery reuses the same native request ID, timestamp, bytes and preconditions.
It can finish an interrupted publication without overwriting a newer write, even
if the target was published before a crash. After success the parts are released,
leaving only a small completion receipt for one hour to answer retries. Abort
atomically deletes an open upload and all its parts. If validation or storage
capacity prevents completion before publication, a four-byte state CAS reopens
it so it can be retried or aborted without rewriting the whole upload.

A maintenance worker runs at startup and every minute. It recovers requested
completions using the owner's current write grant, discards staged parts after
owner/grant revocation, expires uploads idle for 24 hours since their last
committed change, and removes expired one-hour receipts. Uploads being completed
are serialized through durable state/version checks, not a process-local mutex.
These are fixed retention intervals in this first implementation; a transfer
which makes no committed progress before expiry must start again.

The implementation prioritizes atomic reclamation: each changed upload rewrites
its compact native object. It stages snapshots/bodies in immediately unlinked
local files, so local scratch space and I/O scale with the upload working set.
This is functional streaming with bounded RAM, not a zero-copy multipart engine.
The server S3 path supports staged ranges beyond the native WebSocket GET's
current 1-GiB staging budget; the native SDK still inherits its transport limits.

STMU's fixed header is 32 bytes: magic at 0, u16 version 1 at 4, reserved u16 at 6,
u32 state at 8 (open/publishing/done/failed), u32 variable metadata length at 12,
u64 updated Unix ns at 16 and u64 creation Unix ns at 24. Variable metadata uses
the existing Text/Varint codec for owner/key, headers, checksums, sorted part table,
completion recipe and native publication preconditions; it is bounded to 4 MiB.
Part payloads follow in part-number order. Changing a state alone uses Range-CAS.

## TLS through the existing reverse proxy

Local applications can use HTTP on localhost. For remote TLS, preserve the
original signed Host header, exact `/s3/...` path and query. Do not strip the `/s3`
prefix, normalize object keys or rewrite the signed host. Keep native admin URLs
out of a public S3-only proxy location.

For an nginx TLS virtual host with certificates already configured:

```nginx
location /s3/ {
    proxy_pass http://127.0.0.1:7419;
    proxy_set_header Host $http_host;
    proxy_http_version 1.1;
    proxy_request_buffering off;
    client_max_body_size 0;
}
```

The external SDK endpoint is then `https://storage.example.org/s3`. nginx must
connect from an address permitted by STQR's existing subnet rules. STQR uses the
actual peer address, not client-controlled forwarded headers.

The equivalent Apache TLS-vhost fragment is:

```apache
ProxyPreserveHost On
AllowEncodedSlashes NoDecode
ProxyPass        /s3/ http://127.0.0.1:7419/s3/ nocanon
ProxyPassReverse /s3/ http://127.0.0.1:7419/s3/
```

## Format and maintenance

A key hashes to its stable native address, domain-separated from FUSE and other
frontends. **Header, variable metadata and payload are one native object.** PUT
stages and verifies the body, then atomically replaces that object with a native
version precondition. Failed uploads/checksums/publications do not create detached
payload objects. Replacement and deletion release the old native allocations;
there is no S3 garbage object graph requiring a later fsck.

GET checks the native version under the same read handle used to copy its data.
If an overwrite races header resolution, the HTTP adapter retries before sending
headers or bytes. It copies the requested range into an immediately unlinked
snapshot file, releases the volume handle, then streams the snapshot. A slow
network reader therefore does not prevent native overwrite/delete or space
reclamation. The snapshot closes on completion/error; process termination also
releases it. The HTTP adapter stages the requested range without the native WebSocket
GET transport’s current 1-GiB budget.
Use dedicated S3 buckets; FUSE `--fsck` is not an S3 maintenance tool.

All integers in **STS3 v2/v3** are little endian with no implicit padding:

| Offset | Bytes | Field |
| --- | --- | --- |
| 0 | 4 | `STS3` |
| 4 | 2 | version = 2 for ordinary objects, 3 for multipart ETags |
| 6 | 2 | zero in v2; multipart part count in v3 |
| 8 | 4 | flags; reserved status field, bit 0 deleted |
| 12 | 32 | native object OID (self reference) |
| 44 | 8 | payload length |
| 52 | 8 | modification time, Unix nanoseconds |
| 60 | 16 | MD5 ETag bytes |
| 76 | 4 | variable metadata length |
| 80 | variable | Text key, sorted header pairs, sorted user-metadata pairs |
| 80 + metadata length | payload length | payload bytes |

Each pair map is `count:Varint` followed by Text/Text pairs. The fixed header plus
variable metadata is limited to 64 KiB, independently of payload size. Fixed
fields are read directly at their documented offsets; C/Rust packed views must
handle byte order and unaligned integers. Native Range-CAS remains available for
fixed-width metadata changes. DELETE does not leave a flag-only payload behind.
Version 3 uses the same offsets and stores the multipart ETag digest in the
existing 16-byte field, with its part count at offset 6. Version 2 remains readable. Upgrade all S3-serving instances before writing
multipart objects: older v2-only HTTP adapters cannot interpret v3 ETags.
The native storage protocol continues treating both as opaque object bytes.

LIST uses read-only native object inventory, `BUCKET_OBJECT_LIST` (`0x0117`),
then reads each S3 envelope's key/header. There are no separate persisted name
index entries to leak after delete or failed publication. This first listing
implementation scans native IDs and sorts S3 keys in the frontend; it is not a
native lexicographic listing engine or a multi-request snapshot. Native version
history, retry receipts and deletion tombstones follow the native retention
policy; they do not retain deleted payload extents.

Signing secrets use AES-GCM under a key derived from the cluster token, with the
user/key IDs authenticated. Public lists and mutation receipts contain no secrets.
Back up the system bucket together with the cluster configuration. Changing the
cluster token requires resealing or recreating S3 access keys.

Administration also exposes `/api/users/USER_ID/s3-keys`: GET lists IDs, PUT accepts
`{"access_key":"...","secret_key":"..."}`, DELETE `/ACCESS_KEY` revokes it. These
endpoints require normal admin authentication (and CSRF protection for sessions).
Supply `Idempotency-Key` as a nonzero 128-bit hexadecimal ID for mutation retries.
Binary equivalents are USER_S3_KEY_LIST/SET/DELETE (`0x2025`–`0x2027`); mutations
use the existing user-operation receipts and admin-draft machinery.

## Verification

The Go integration tests use disposable nodes/buckets and exercise publication,
concurrency, checksums, ranges, pagination, native deletion/reclamation, key persistence,
revocation and read-only/write-only/delete-only grants. Physical-space regression tests repeatedly overwrite more bytes than the volume
capacity, delete the key and verify that payload allocations return to baseline.
They also cover aborted/checksum-failed uploads and a blocked download concurrent
with overwrite/delete. No existing daemon or bucket is used. The optional PHP test runs the real AWS SDK, including streaming
above 16 MiB, SaveAs, ranges, both list APIs and presigned URLs.

```sh
go test -race ./server -run '^TestS3' -count=1
# Install aws/aws-sdk-php in a separate scratch directory, then:
STQR_S3_PHP_AUTOLOAD=/path/to/vendor/autoload.php \
    go test -race ./server -run '^TestS3PHPClient$' -count=1
```

The extended compatibility suite also runs current AWS CLI v2 and rclone,
including their multipart and server-side copy paths:

```sh
STQR_TEST_AWS_CLI=/path/to/aws \
STQR_TEST_RCLONE=/path/to/rclone \
STQR_S3_PHP_AUTOLOAD=/path/to/vendor/autoload.php \
    go test -race ./server -run '^TestS3' -count=1
```

Tests cover AWS's published streaming-signature vector, corrupted chunks/trailers,
CRC64NVME's check vector, restart recovery, a crash after target publication,
revoked grants, full-storage abort, replaced-part reclamation and expiry cleanup.
